# Data pipeline: locations/parking import and image storage

This covers the two-step production data pipeline and the image storage strategy it assumes. `scripts/data/README.md` (Member 4) covers normalization/validation in detail; this document picks up from a validated normalized file.

## Pipeline order

```text
raw provider data
  -> pnpm data:normalize   (scripts/data/normalizer.ts, Member 4)
  -> normalized.json
  -> pnpm data:import       (scripts/data/import.ts, this doc -- locations + parking only)
  -> pnpm embeddings:prepare + pnpm embeddings:import  (scripts/embeddings/*, Member 1 -- location_images + vectors)
```

**Run the locations/parking importer before the embeddings importer.** `location_images.location_id` is a foreign key to `locations.id`; `scripts/embeddings/importer.ts` already preflights this itself (`findLocationIds` / "Missing location_id values"), so running embeddings import first simply fails its own check rather than corrupting anything -- but there is no reason to hit that failure when the order above avoids it.

`scripts/data/import.ts` does **not** read or write `location_images` or embeddings at all -- that stays entirely on the embeddings pipeline (`docs/offline-embeddings.md`), so there is nothing to keep in sync between the two importers beyond `locations.id` existing first.

## `pnpm data:import`

Validates a normalized file with `scripts/data/validator.ts` (Member 4's validator, reused as-is -- not reimplemented) and upserts the locations and parking it describes.

```bash
# 1. Validate + report only, no database credentials needed.
pnpm data:import data-work/normalized/provider.json data-work/reports/import.json

# 2. Connect and report expected insert/update counts, write nothing.
SUPABASE_URL=https://PROJECT.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=... \
pnpm data:import data-work/normalized/provider.json data-work/reports/import.json --dry-run

# 3. Apply.
SUPABASE_URL=https://PROJECT.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=... \
pnpm data:import data-work/normalized/provider.json data-work/reports/import.json --apply --batch-size 50
```

- `--validate-only` (default): runs the validation gate and reports expected counts; no database connection is attempted or required.
- `--dry-run`: connects and checks which location ids / `(location_id, name)` parking pairs already exist, so the printed `toInsert`/`existing` counts are accurate, but issues no writes.
- `--apply`: upserts for real. Locations are written before parking (foreign key).
- `--image-root`: resolves each location's `images[].imagePath`. Import is always a local-asset-gated operation, equivalent to the validator's explicit `--require-local-assets` mode; clean-clone production metadata checks instead use `pnpm data:validate ... --metadata-only` as documented in `scripts/data/README.md`.
- `--batch-size`: 1–500, default 100.

**A record that fails validation is skipped, not fatal to the run.** The import report uses the shared validator's mode/summary/error fields; the standalone `data:validate` report additionally records input file identities and preserves an approved report by writing failures to a mode-specific sibling. Every skipped location's errors are also echoed to the console. Every other, valid location in the same file is still imported. The process exits with status 1 if anything was skipped, so CI/an operator notices, but the valid subset is still written.

### Upsert keys

- **`locations`**: by `id`. `scripts/data/normalizer.ts` passes an already-existing, source-provided UUID straight through (it does not generate one -- see `mapping.example.json`'s `fields.id`), and `scripts/data/validator.ts` requires every imported record to have a UUID-formatted `id`. Re-running normalize on the same raw input is therefore deterministic, so upserting by `id` is safe: re-running the whole pipeline on unchanged source data updates the same rows instead of duplicating them. (Confirmed by reading `normalizer.ts`/`validator.ts` directly -- there is no `crypto.randomUUID()` or hash-based id generation anywhere in that pipeline.)
- **`parking`**: by `(location_id, name)` (`supabase/migrations/20260929000000_parking_upsert_key.sql`, a new unique constraint). `CanonicalParkingRecord.id` (`scripts/data/contracts.ts`) is optional and not validated as a UUID, so it is not usable as a reliable primary key the way `locations.id` is; this importer ignores it entirely. `parking.id` keeps being generated by its column default on first insert and is left untouched on every later upsert of the same `(location_id, name)` pair -- verified directly: two `--apply` runs of the same input left the same `parking.id` in place and did not change the row count.

### Environment / admin client

Uses a new shared script-only Supabase admin client, `scripts/shared/supabase-admin-client.ts` -- the same `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` variables `scripts/embeddings/import.ts` already uses (see `.env.example`), with the same guards (rejects a service role key placed under a `NEXT_PUBLIC_*` name, requires HTTPS unless the host is `localhost`/`127.0.0.1`). It does **not** `import "server-only"`, unlike `src/infrastructure/supabase/admin-client.ts` (the Next.js-side admin client) -- that import throws unconditionally under plain Node execution, which is how every script here runs (see the module's own comment for how this was confirmed). `scripts/embeddings/import.ts` (Member 1's file) still implements this same logic inline rather than importing the shared module; not changed here, see the report for this change for the proposed diff.

**No public write API.** This importer is the only way real location/parking rows can be created or changed -- there is no `POST`/`PUT` route under `src/app/api/**` for it, matching the existing RLS design (`anon`/`authenticated` only ever get `SELECT`; every write requires the service role -- see `docs/database.md`'s "RLS verification").

## Image storage strategy

Only store images the project has confirmed rights to publish -- either uploaded to Supabase Storage, or an authorized external URL the project does not host. Record source/license/attribution in `DATA_LICENSES.md` before committing real records or images, same as the existing rule for location data.

### `location_images` columns (already in the schema, see `docs/database.md`)

| Column | Meaning |
| --- | --- |
| `image_url` | The URL the app actually loads the image from -- a Supabase Storage public URL, or an authorized external URL |
| `source` | Who/what the image came from (photographer, agency, authorized dataset name) -- independent of `locations.source` |
| `storage_path` | Set only when the image is hosted in Supabase Storage (`location-images` bucket, see below); `null` when `image_url` points at an authorized external host instead |

### Storage vs. external URL

Prefer Supabase Storage (a `storage_path` is set) whenever the project has the right to re-host the file -- it survives the original source disappearing or changing its URL structure, and its `location-images` bucket (below) has a size/type ceiling the app already enforces client-side. Use an authorized external URL only when re-hosting is not permitted by the license/agreement, or the file must remain the source's own canonical copy. **Decision needed with Member 4**: the exact threshold for "prefer Storage" per source/license type is a licensing judgment call, not a technical one -- flagged for the team, not decided unilaterally here.

### Storage bucket

`supabase/migrations/20260929010000_location_images_storage_bucket.sql` creates a `location-images` bucket: `public = true` (read), a 15 MB file-size limit and JPEG/PNG/WebP MIME allow-list matching `src/lib/ai/embedding-service.ts`'s existing client-side limits, and a `select`-only RLS policy on `storage.objects` for `anon`/`authenticated` -- no insert/update/delete policy, so only the service role can write, the same pattern as every table in this project. Verified against a real `supabase start` instance (`supabase/tests/schema-and-rls.integration.test.ts`, see [integration testing](integration-testing.md)): the bucket exists and is public, an anon-key client's upload is rejected by RLS, and the service role's upload succeeds and is then readable at its public URL.

### `storage_path` convention

```text
locations/{location_id}/{source}-{source_image_key}.{ext}
```

- `{location_id}`: the owning `locations.id` (UUID).
- `{source}`: same value as `location_images.source` (e.g. a provider name), lowercased, non-alphanumeric characters replaced with `-`.
- `{source_image_key}`: a stable identifier for this specific image *within its source* -- the source's own image/asset ID if it has one, otherwise a content hash (e.g. SHA-256 of the file, hex-encoded) computed once when the file is first prepared for upload. This is a **naming convention for the path string**, not a new database column -- `location_images` has no separate `source_image_key` column, and none is needed.
- `{ext}`: `jpg`, `png`, or `webp`, matching the actual file content (do not trust a client-supplied extension).

### De-duplication

`location_images` already has a partial unique index on `(location_id, storage_path)` (`supabase/migrations/20260928000000_location_data_integrity.sql`), enforced whenever `storage_path` is set. Because the convention above makes `storage_path` a **deterministic function of `(source, source_image_key)`**, re-uploading the same source image for the same location always produces the same `storage_path` and is naturally rejected as a duplicate by that existing constraint -- no new schema is required, only the naming discipline above. A content-hash-based `source_image_key` additionally protects against the same file being re-published under a different filename from the same source; a provider-assigned key does not, so prefer a content hash when the source doesn't already give every image a stable ID of its own.

## Open decisions for the team

- **License/attribution display**: where and how a location's image license/attribution shows up in the UI (or whether it's only recorded in `DATA_LICENSES.md` and not surfaced) -- Member 2/4 call, not decided here.
- **Storage vs. external URL threshold**: see above -- Member 4 (data rights) call.
- **`source_image_key` source**: whether Member 4's normalized output should start carrying a stable per-image key (provider ID or precomputed hash) so whoever prepares Storage uploads doesn't have to compute it ad hoc -- would be a `scripts/data/contracts.ts` change, Member 4's file.
- **`parking`'s `(location_id, name)` upsert key doesn't survive a rename.** If a source dataset renames a parking spot between import runs (same physical lot, different `name`), this importer creates a *second* `parking` row rather than updating the first one -- there is no stable identifier it can use instead today (see "Upsert keys" above: `CanonicalParkingRecord.id` is optional and not UUID-validated, so it isn't reliable either). Not fixed here -- flagged for the team: either accept the limitation (parking listings are low-stakes and low-churn), have Member 4's normalizer start emitting a stable per-parking-spot id the same way it already does for locations, or add an explicit "retire this parking row" step to the importer once a real duplicate is observed.
