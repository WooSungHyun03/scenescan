Migrations, applied in order:

1. `supabase/migrations/20260920000000_initial_schema.sql` — tables, indexes, RLS, initial `match_location_images` RPC.
2. `supabase/migrations/20260928000000_location_data_integrity.sql` — provenance/freshness columns, `updated_at` triggers, image de-duplication. Does not modify the first migration or the RPC contract.
3. `supabase/migrations/20260928010000_match_location_images_filters.sql` — replaces `match_location_images` (same name, extended signature) to add SQL-side `filter_region`/`filter_category` and `expected_embedding_model` gating. See [search ranking](search-ranking.md) for the full RPC contract and a reproducible regression test.
4. `supabase/migrations/20260928020000_drop_embedding_provenance_defaults.sql` — drops the temporary column defaults on `location_images.embedding_model` and `locations.source` added in migration 2 (both stay `not null`).
5. `supabase/migrations/20260928030000_match_location_images_exclude_location.sql` — replaces `match_location_images` again to add `exclude_location_id`, used by `GET /api/locations/[id]/similar` to drop a location's own images from its own similar-locations search. See [search ranking](search-ranking.md).
6. `supabase/migrations/20260929000000_parking_upsert_key.sql` — adds a `unique (location_id, name)` constraint on `parking`, the upsert key `scripts/data/import.ts` uses. See [data pipeline](data-pipeline.md).
7. `supabase/migrations/20260929010000_location_images_storage_bucket.sql` — creates the public-read `location-images` Storage bucket and its read-only RLS policy. Not verified against a disposable Postgres container (`storage` is a Supabase-platform schema); see [data pipeline](data-pipeline.md) for the manual verification steps.

| Table | Purpose |
| --- | --- |
| `locations` | Identity, descriptive data, region/category, coordinates, permit contact, small noise metadata JSONB, source/freshness provenance |
| `location_images` | Multiple images per location; nullable `extensions.vector(512)` for offline backfill; embedding provenance |
| `parking` | Nearby parking; optional location link; source/freshness provenance |

The 512 dimensions match the chosen CLIP image feature extractor's documented output. Cosine distance (`<=>`) is used in the RPC, following [Supabase's pgvector guidance](https://supabase.com/docs/guides/ai/semantic-search). The migrations enable pgvector, read-only RLS policies for `anon`/`authenticated`, and an invoker-rights RPC. No client write policy is created — inserts/updates/deletes require the service role, used only by controlled scripts. Start with sequential vector scans for a small student dataset; add a cosine HNSW index after measuring dataset size and query cost.

`match_location_images` clamps similarity threshold to 0–1 and match count to 1–200, and (as of migration 3) also filters by region/category and by `embedding_model` inside the query itself — see [search ranking](search-ranking.md) for the full parameter/return contract. API validation additionally rejects malformed, non-finite, wrong-dimension, and all-zero queries before they reach pgvector. Empty tables return an empty result. Offline import validates every vector, verifies location foreign keys and existing image ownership, probes the RPC, and only then allows controlled service-role upserts. See [offline embeddings](offline-embeddings.md).

Run `pnpm embeddings:audit-schema` after migration edits. Treat its "12 checks passed" output as auditing history, not the live RPC contract, until it's extended (flagged as a suggestion for Member 1 to consider). Mock fixture rows (`src/domains/locations/fixtures/locations.ts`) use fixed UUIDs (`00000000-0000-4000-8000-000000000001`..`010`) so mock mode exercises the same uuid-shaped code paths a real row would; `demo-01`..`demo-10` survive only as each fixture's `slug` field, used to keep pointing at `public/images/demo-0N.svg` without renaming those files. `location_images.image_url` should point to an image the project has rights to publish, preferably in a public Supabase Storage bucket. ## Constraints and defaults

- `region`/`category` are restricted by `check` constraints to the same values as `src/types/domain.ts` (`Region`, `LocationCategory`). Update the constraint and the TypeScript type together if this list ever changes.
- Foreign keys: `location_images.location_id` and `parking.location_id` both reference `locations.id`. Images cascade-delete with their location (`on delete cascade`); parking only unlinks (`on delete set null`) since a parking spot can outlive or stand apart from a specific filming location.
- All three tables have `created_at` and `updated_at` (`timestamptz`, not null, default `now()`); `updated_at` is refreshed by a `before update` trigger (`public.set_updated_at`), not by application code.
- `location_images.embedding_model` is `not null` (no default as of migration 4) and records the model ID + revision that produced the row's vector, formatted as `<model_id>@<revision>` (e.g. `Xenova/clip-vit-base-patch32@main`, matching `CLIP_MODEL_ID`/`CLIP_MODEL_REVISION` in `src/lib/ai/embedding-service.ts`). `match_location_images`'s `expected_embedding_model` parameter compares against this column exactly and fails closed (matches nothing) if it's null or doesn't match — see [search ranking](search-ranking.md). Runtime (browser) and offline embeddings must share this value, or search quality degrades without an obvious error, and now inserts fail loudly instead of silently defaulting. **The offline importer (`scripts/embeddings/importer.ts`) does not currently set this column** — since migration 4 removed the default, any insert through the current importer will fail with a `not_null` violation until it's updated to pass this explicitly. Confirm the exact value (including whether a quantized `dtype` is in play) with Member 1, then update the importer.
- `location_images` has a partial unique index on `(location_id, storage_path)` (only enforced when `storage_path` is set) to stop the same stored file from being imported twice for one location. `storage_path` and `source` are nullable and not yet populated by the current importer.
- `locations.source`, `locations.reference_date`, and `locations.last_verified_at` — together with the pre-existing `source_url` — mirror the `DataProvenance` shape already produced by `scripts/data/normalizer.ts` (`source`, `sourceUrl`, `referenceDate`, `lastVerifiedAt`). `source` is `not null` with no default as of migration 4 (was `'manual'`); hand-entered/manual rows must now pass `source = 'manual'` explicitly. `parking.last_verified_at` and `parking.reference_date` mirror the same shape for `CanonicalParkingRecord.provenance`; `parking.source` already existed.
- There is intentionally no separate `source_id`/upsert-key column on `locations`: `scripts/data/normalizer.ts` already assigns an optional, pre-generated UUID as the canonical record's own `id` (validated in `scripts/data/validator.ts`), so `locations.id` is the natural upsert key — the same pattern `scripts/embeddings/importer.ts` already uses to upsert `location_images` by `id`. **Confirmed**: `scripts/data/import.ts` (see [data pipeline](data-pipeline.md)) upserts `locations` by `id` on exactly this basis. `parking` has its own `unique (location_id, name)` upsert key (migration 6) since `CanonicalParkingRecord.id` is optional and not UUID-validated, unlike `locations.id`.

## RLS verification

Automated as `supabase/tests/schema-and-rls.integration.test.ts` (see [integration testing](integration-testing.md)) against a real `supabase start` instance, not an ad-hoc Postgres container with hand-picked grants -- that distinction matters, see below.

**Supabase's real platform bootstrap grants `anon`/`authenticated` every table privilege by default** (`select grantee, privilege_type from information_schema.role_table_grants where grantee = 'anon'` lists `SELECT`, `INSERT`, `UPDATE`, `DELETE`, ... on every `public` table) -- access is restricted entirely by RLS policies, not by withholding `GRANT`s. No migration in this project grants `INSERT`/`UPDATE`/`DELETE` to `anon`/`authenticated` either; that's irrelevant to the actual enforcement mechanism, which is Supabase's own default privileges, not anything these migrations control.

With RLS enabled and only a `select`-for-`anon,authenticated` policy defined (which is all every migration here creates), Postgres enforces the missing write policies differently per command:

- **`INSERT`**: rejected outright with `new row violates row-level security policy` (an error), because `WITH CHECK` defaults to `false` when no policy applies.
- **`UPDATE`/`DELETE`**: **do not error**. RLS applies an implicit `USING (false)` for the missing policy, so the command "succeeds" but matches and affects zero rows -- the row is left completely unchanged. Verified directly: seed a row as the service role, attempt `update ... set name = 'HACKED BY ANON'` and `delete` as `anon`, then re-read the row with the service role -- it's untouched and still present.

Both outcomes are equally safe (no anon-originated write ever takes effect), but only the first is a client-visible error. Do not write code, docs, or tests that assume an `UPDATE`/`DELETE` attempt by `anon` throws -- check that the data didn't change instead. (An earlier version of this document, based on ad-hoc verification against a hand-built Postgres+PostgREST container that manually granted only `SELECT` to `anon`, incorrectly claimed all three commands throw `permission denied for table X`; that was accurate for that non-representative setup, not for real Supabase.)

`match_location_images` is `security invoker`, so it runs with the caller's own privileges; calling it as `anon` was verified to succeed and return the same rows as a service-role call, confirming the base `SELECT` grant is sufficient for the function's internal join. Storage RLS on the `location-images` bucket (`supabase/migrations/20260929010000_location_images_storage_bucket.sql`) was verified the same way: `anon` upload is rejected with a real error (storage's own RLS `WITH CHECK` on `storage.objects` insert), the service role's upload succeeds, and the resulting object is then readable by an unauthenticated request to its public URL.
