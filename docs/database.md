# Database

Migrations, applied in order:

1. `supabase/migrations/20260920000000_initial_schema.sql` — tables, indexes, RLS, initial `match_location_images` RPC.
2. `supabase/migrations/20260928000000_similar_locations.sql` — adds `match_similar_location_images`, a separate RPC for `GET /api/locations/[id]/similar` (Member 1). Does not touch `match_location_images`.
3. `supabase/migrations/20260929000000_scale_location_catalog.sql` — widens the `locations.region` check constraint to all 17 Korean first-level regions and adds a cosine HNSW index on `location_images.embedding`.
4. `supabase/migrations/20261001000000_location_attribution.sql` — adds nullable `source`/`author`/`license`/`license_url`/`last_verified_at` on `locations` and `source`/`source_url`/`author`/`license`/`license_url`/`last_verified_at` on `location_images`, all for end-user-facing attribution display (see `SourceMetadata` in `src/types/domain.ts`). HTTP(S)-only checks on the `*_url` columns.
5. `supabase/migrations/20261001000001_location_import_metadata.sql` — adds `locations.import_batch` (scripts/data batch-provenance tag; deliberately *not* named `source` — see below), `locations.reference_date`, `location_images.embedding_model`, `location_images.storage_path`, and `updated_at` + triggers on all three tables. Does not touch migration 4's attribution columns.
6. `supabase/migrations/20261001000002_drop_import_metadata_defaults.sql` — drops the temporary column defaults on `location_images.embedding_model` and `locations.import_batch` added in migration 5 (both stay `not null`).
7. `supabase/migrations/20261001000003_match_location_images_filters.sql` — replaces `match_location_images` (same name, extended signature) to add SQL-side `filter_region`/`filter_category` and `expected_embedding_model` gating. See [search ranking](search-ranking.md) for the full RPC contract and a reproducible regression test.
8. `supabase/migrations/20261001000004_parking_upsert_key.sql` — adds a `unique (location_id, name)` constraint on `parking`, the upsert key `scripts/data/import.ts` uses. See [data pipeline](data-pipeline.md).
9. `supabase/migrations/20261001000005_location_images_storage_bucket.sql` — creates the public-read `location-images` Storage bucket and its read-only RLS policy. Not verified against a disposable Postgres container (`storage` is a Supabase-platform schema); see [data pipeline](data-pipeline.md) for the manual verification steps.
10. `supabase/migrations/20261002000000_filtered_location_search.sql` (`origin/main`) — adds `match_location_images_filtered`: region/category filters are applied before ranking, and `distinct on (location_id)` picks the single highest-similarity image per place, so `match_count` directly caps the number of *places* returned rather than a raw image candidate pool. Fixes the same class of bug migration 7 fixed for `match_location_images` (a fixed top-N image cutoff could starve a filter once the catalog grew past it), via a second, additive RPC instead of changing `match_location_images` itself.
11. `supabase/migrations/20261002000001_match_location_images_filtered_model.sql` — adds `expected_embedding_model` to `match_location_images_filtered`, matching `match_location_images`'s own parameter/semantics (see below). Backend-owned follow-up to migration 10.

Migrations 5–9 were renumbered to run after migration 4 (`20261001000000_location_attribution.sql`, from `origin/main`) when this branch was merged: they had never been applied to any real Supabase project at that point, while migration 4 already had been, so sequencing them after it (rather than main re-sequencing around this branch's then-earlier timestamps) kept a single order valid for both a fresh database and the real deployed one. See the merge report for the full analysis, including why migration 5 originally named its batch-provenance column `locations.source` and had to be renamed to `import_batch` (below) and why a since-removed `exclude_location_id` migration for `match_location_images` was dropped entirely once `match_similar_location_images` (migration 2) was adopted for similar-locations search instead.

| Table | Purpose |
| --- | --- |
| `locations` | Identity, descriptive data, region/category, coordinates, permit contact, small noise metadata JSONB, attribution metadata, scripts/data import-batch provenance |
| `location_images` | Multiple images per location; nullable `extensions.vector(512)` for offline backfill; embedding provenance; attribution metadata |
| `parking` | Nearby parking; optional location link; source/freshness provenance |

The 512 dimensions match the chosen CLIP image feature extractor's documented output. Cosine distance (`<=>`) is used in all three RPCs, following [Supabase's pgvector guidance](https://supabase.com/docs/guides/ai/semantic-search). The migrations enable pgvector, read-only RLS policies for `anon`/`authenticated`, and invoker-rights RPCs. No client write policy is created — inserts/updates/deletes require the service role, used only by controlled scripts. Start with sequential vector scans for a small student dataset; migration 3 already adds a cosine HNSW index ahead of the production catalog's scale -- at the current (low hundreds of images) scale an exact scan/group is inexpensive and avoids approximate-index recall issues; measure again before growing by orders of magnitude.

`match_location_images` clamps similarity threshold to 0–1 and match count to 1–200, and (as of migration 7) also filters by region/category and by `embedding_model` inside the query itself — see [search ranking](search-ranking.md) for the full parameter/return contract. `match_location_images_filtered` (migration 10, `origin/main`, with migration 11's `expected_embedding_model` added) additionally deduplicates to one image per location in SQL (`distinct on (location_id)`), so its `match_count` caps the number of places returned, not a raw image pool -- `searchSupabaseLocations` uses this RPC as its primary path, falling back to `match_location_images` only for an unfiltered query while migration 10/11 are not yet applied (see `src/domains/locations/server/supabase-repository.ts`; a filtered query during that rollout window fails explicitly rather than silently returning unfiltered results). `match_similar_location_images` (migration 2, Member 1) computes a representative vector as the mean of all non-null embeddings belonging to the selected location, excludes that location inside SQL, uses the same cosine distance and threshold/count bounds, and orders equal distances by location and image UUID; it does not have an `expected_embedding_model` parameter (flagged as a proposal for Member 1, not fixed here). API validation additionally rejects malformed, non-finite, wrong-dimension, and all-zero queries before any RPC runs. Empty tables return an empty result. Offline import validates every vector, verifies location foreign keys and existing image ownership, probes the RPC, and only then allows controlled service-role upserts. See [offline embeddings](offline-embeddings.md).

Run `pnpm embeddings:audit-schema` after migration edits. It is a static audit of the committed SQL files; whether it has been kept in sync with this branch's renamed/renumbered migrations (above) was not independently re-verified here. Run `pnpm embeddings:import output.json --dry-run` against each target project to verify the deployed RPC and referenced rows without writing.

Mock fixture rows (`src/domains/locations/fixtures/locations.ts`) use fixed UUIDs so mock mode exercises the same uuid-shaped code paths a real row would — confirmed against the real production catalog (`data/production/locations.json`), whose `id`s are also UUIDs. `location_images.image_url` should point to an image the project has rights to publish, preferably in a public Supabase Storage bucket. Do not import external location datasets until their terms are checked.

## Constraints and defaults

- `region`/`category` are restricted by `check` constraints to the same values as `src/types/domain.ts` (`Region`, `LocationCategory`, both derived from `src/types/location-options.ts`). Update the constraint and the TypeScript type together if this list ever changes.
- Foreign keys: `location_images.location_id` and `parking.location_id` both reference `locations.id`. Images cascade-delete with their location (`on delete cascade`); parking only unlinks (`on delete set null`) since a parking spot can outlive or stand apart from a specific filming location.
- All three tables have `created_at` and `updated_at` (`timestamptz`, not null, default `now()`); `updated_at` is refreshed by a `before update` trigger (`public.set_updated_at`), not by application code.
- `location_images.embedding_model` is `not null` (no default as of migration 6) and records the model ID + revision that produced the row's vector, formatted as `<model_id>@<revision>` (e.g. `Xenova/clip-vit-base-patch32@main`, matching `CLIP_MODEL_ID`/`CLIP_MODEL_REVISION` in `src/lib/ai/embedding-service.ts`). `match_location_images`'s and `match_location_images_filtered`'s `expected_embedding_model` parameter is an *optional* filter, not fail-closed: a non-null value restricts candidates to rows whose `embedding_model` matches exactly, and `null` applies no restriction (same null-means-unrestricted convention as `filter_region`/`filter_category`) — see [search ranking](search-ranking.md). Application code always passes it explicitly (never relies on the null default); the column itself does not record `CLIP_MODEL_DTYPE` (`src/lib/ai/embedding-service.ts`), so a future dtype change is invisible to this filter -- see search-ranking.md's follow-up note. Migration 5's default backfills every row that already existed when it ran (confirmed: `alter table ... add column ... not null default ...` fills existing rows with the default as part of the same statement), so the real production catalog's locations/images get the correct value automatically; migration 6 then drops that default so a future insert that omits the column fails loudly instead of silently inheriting today's placeholder. **`origin/main`'s offline importer (`scripts/embeddings/import.ts`) and `scripts/data/production-importer.ts` do not currently set this column** — any new row inserted through either after this merge will fail with a `not_null` violation until updated to pass this explicitly (see [data pipeline](data-pipeline.md) and `docs/security-checklist.md`'s pre-merge checklist; both files are Member 1's and were not changed here).
- `location_images` has a partial unique index on `(location_id, storage_path)` (only enforced when `storage_path` is set) to stop the same stored file from being imported twice for one location. `storage_path` is nullable and not yet populated by the current importer.
- `locations.import_batch` and `locations.reference_date` mirror part of the `DataProvenance` shape already produced by `scripts/data/normalizer.ts` (`source`, `referenceDate`) for `scripts/data/location-importer.ts`'s own upsert — deliberately *not* named `locations.source`, because migration 4 already uses that exact name for a different, user-facing concept (the human-readable attribution source shown in the UI). The two are unrelated data even though they'd otherwise share a column name; see the merge report for how this was caught before either migration had ever been applied anywhere. `import_batch` is nullable with no default (not `not null` -- an earlier draft of migration 5 made it `not null default 'manual'`, but `origin/main`'s own `scripts/data/production-importer.ts` writes `locations` rows directly with no concept of a scripts/data import batch, so a forced default would mislabel every one of its rows; `null` means "not written by scripts/data"). `locations.last_verified_at` comes from migration 4, not migration 5 (migration 5 originally also added it with `DataProvenance.lastVerifiedAt` in mind, but since the two concepts are close enough and migration 4 already provides the column, migration 5 was edited to not re-add it). `parking.last_verified_at`, `parking.reference_date`, and `parking.source` are untouched by migration 4 (which does not modify `parking`) and keep their original `DataProvenance`-shaped meaning.
- There is intentionally no separate `source_id`/upsert-key column on `locations`: `scripts/data/normalizer.ts` already assigns an optional, pre-generated UUID as the canonical record's own `id` (validated in `scripts/data/validator.ts`), so `locations.id` is the natural upsert key — the same pattern `scripts/embeddings/importer.ts` already uses to upsert `location_images` by `id`. **Confirmed**: `scripts/data/import.ts` (see [data pipeline](data-pipeline.md)) upserts `locations` by `id` on exactly this basis. `parking` has its own `unique (location_id, name)` upsert key (migration 8) since `CanonicalParkingRecord.id` is optional and not UUID-validated, unlike `locations.id`.

## RLS verification

Automated as `supabase/tests/schema-and-rls.integration.test.ts` (see [integration testing](integration-testing.md)) against a real `supabase start` instance, not an ad-hoc Postgres container with hand-picked grants -- that distinction matters, see below.

**Supabase's real platform bootstrap grants `anon`/`authenticated` every table privilege by default** (`select grantee, privilege_type from information_schema.role_table_grants where grantee = 'anon'` lists `SELECT`, `INSERT`, `UPDATE`, `DELETE`, ... on every `public` table) -- access is restricted entirely by RLS policies, not by withholding `GRANT`s. No migration in this project grants `INSERT`/`UPDATE`/`DELETE` to `anon`/`authenticated` either; that's irrelevant to the actual enforcement mechanism, which is Supabase's own default privileges, not anything these migrations control.

With RLS enabled and only a `select`-for-`anon,authenticated` policy defined (which is all every migration here creates), Postgres enforces the missing write policies differently per command:

- **`INSERT`**: rejected outright with `new row violates row-level security policy` (an error), because `WITH CHECK` defaults to `false` when no policy applies.
- **`UPDATE`/`DELETE`**: **do not error**. RLS applies an implicit `USING (false)` for the missing policy, so the command "succeeds" but matches and affects zero rows -- the row is left completely unchanged. Verified directly: seed a row as the service role, attempt `update ... set name = 'HACKED BY ANON'` and `delete` as `anon`, then re-read the row with the service role -- it's untouched and still present.

Both outcomes are equally safe (no anon-originated write ever takes effect), but only the first is a client-visible error. Do not write code, docs, or tests that assume an `UPDATE`/`DELETE` attempt by `anon` throws -- check that the data didn't change instead. (An earlier version of this document, based on ad-hoc verification against a hand-built Postgres+PostgREST container that manually granted only `SELECT` to `anon`, incorrectly claimed all three commands throw `permission denied for table X`; that was accurate for that non-representative setup, not for real Supabase.)

`match_location_images` is `security invoker`, so it runs with the caller's own privileges; calling it as `anon` was verified to succeed and return the same rows as a service-role call, confirming the base `SELECT` grant is sufficient for the function's internal join. Storage RLS on the `location-images` bucket (`supabase/migrations/20260929010000_location_images_storage_bucket.sql`) was verified the same way: `anon` upload is rejected with a real error (storage's own RLS `WITH CHECK` on `storage.objects` insert), the service role's upload succeeds, and the resulting object is then readable by an unauthenticated request to its public URL.
